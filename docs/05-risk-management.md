# 05. リスク管理・安全装置

**完全自動で発注する以上、安全装置は戦略本体より重要。**
戦略が間違っていても損失は限定的だが、安全装置が壊れていると青天井になる。

**16項目すべてを Phase 3 で実装する。** ひとつでも欠けたままペーパートレードに進まない。

## 設計原則

### 原則1: 危険な操作ほど通過点を1本に絞る

安全装置は「複数箇所でチェックする」より「**1箇所を必ず通す**」方が確実。
チェック漏れの経路が生まれないため。

- **全発注は `risk/leverage.py` を必ず通る**（#1）— バイパス経路を作らない
- **全建玉クローズは `execution/close_all.py` に集約**（#2）— 大引けと緊急停止で共用

### 原則2: 最重要のコードパスは毎日実行して信頼性を稼ぐ

`close_all.py` は大引けの定時クローズで**毎営業日必ず走る**。
ペーパートレードの3ヶ月間で約60回実行され、そこで壊れていれば必ず露見する。

**滅多に走らないコードは、いざという時に動かない。**
緊急停止のクローズ処理を定時クローズと同じコードにするのは、この理由による。

### 原則3: 状態のズレを抱えて動き続けない

想定建玉とAPI実建玉が食い違ったら、**推測で続行せず停止する**（#10）。
ズレたまま自動発注を続けるのが最も危険。

### 原則4: 失敗は必ず観測可能にする

- クローズ後は `GET /positions` で**残存を実測確認**する（成功したはずと仮定しない）
- 全発注を**事後に完全再現できる粒度**でログに残す（#15）
- プロセスが死んだこと自体を検知する（#16）

## 主要な装置の詳細

### #1 レバレッジ1倍強制

```
建玉総額（買建 + 売建の合計） + 新規発注額 > 現金残高
  → 発注を拒否する
```

**バイパス経路を作らない。** 全発注がこの関数を通る構造にする。
02-margin-rules.md の不変条件をコードで守る仕組み。

### #2 大引け前 全建玉クローズ

デイトレ信用の建玉を当日中に返済し損ねると、
**翌営業日に強制決済され1注文2,200円**（月利目標の約2日分）。

```
14:50  全建玉を成行クローズ発注
   ↓
       GET /positions で残存確認
   ↓
残存あり → 再試行 + アラート
残存なし → 正常終了をログ
```

> 実行時刻 14:50 は暫定値。大引け直前は板が薄くスリッページが増えるため、
> ペーパー期間の実測で調整する。

### #4/#5/#6 損失ブレーカーの三層構造

| 層 | 発動条件 | 動作 | 復帰 |
|---|---|---|---|
| 日次 | 当日 -2% | 当日全停止 + 全クローズ | 翌営業日に自動復帰 |
| 連続 | 3営業日連続マイナス | 自動停止 | **人の明示承認が必要** |
| 累積 | ピークから -15% | 全停止 | **人の明示承認が必要** |

日次は自動復帰、連続と累積は**人の判断を要求する**。
連続して負けているのは戦略が現在の相場に合っていない可能性があり、
自動で再開すると損失を垂れ流すため。

### #7 ポジション制限 — 25%という値の根拠

**この25%は恣意的な数字ではない。他の2つの安全装置から逆算された値。**

損切りは `1.5 × ATR`（`config/strategies.yaml`）、Layer 2 の ATR% 下限は 2%。
したがって1敗あたりの総資産インパクトは `上限比率 × ATR% × 1.5`:

| 上限 | ATR 2% | ATR 3% | ATR 4% |
|---:|---:|---:|---:|
| **25%** | -0.75% | -1.12% | -1.50% |
| 33% | -0.99% | -1.49% | -1.98% |
| 40% | -1.20% | -1.80% | **-2.40%** ✗ |
| 60% | -1.80% | **-2.70%** ✗ | **-3.60%** ✗ |

✗ = **1敗で日次損失上限（#4、-2%）に到達し当日全停止**。

25%なら最悪でも -1.50% で、1敗が当日を終わらせない。

**つまり上限比率を緩めることは、実質的に日次ブレーカーの無効化に等しい。**
「1銘柄あたりの上限を上げるだけ」に見えて、壊れるのは別の装置のほう。

#### この値が決めている他のこと

| 由来 | 導かれる値 |
|---|---|
| 資金 × 25% ÷ 100株 | **取引可能な最大株価 1,250円**（ユニバースの上限） |
| 資金 ÷ `max_concurrent`(5) ÷ 100株 | **通常枠の上限 1,000円** |
| 資金 × 25% | **1銘柄あたりの目標建玉額の上限 12.5万円** |
| 日次ブレーカー ÷ (25% × 1.5) | **ATR% の上限 5.33%**（`risk/limits.py` の `max_atr_pct`） |

#### ATR% 上限がなぜ安全装置なのか

Layer 2 のスコアは **ATR% に最大の重み（0.40）** を置いている。
値幅がないとコスト負けするので下限（2%）は当然だが、
**上限がないとスコアリング自体が「1敗で当日が終わる銘柄」を上位に押し上げる。**

実測（2026-05-29）では ATR% の最大が17.12%あり、上位10銘柄のうち2つが
一律25%で建てると1敗 -2% を超えていた。下限だけでは守れない。

#### 何敗まで耐えられるか

**1単元100株が最小単位なので、1敗のインパクトはこれ以上小さくできない。**
実測で選定された銘柄の1敗は中央値 -0.86%、最悪 -1.46%。
つまり**2〜3敗で当日が停止する**。`docs/04` のトレード頻度想定（3〜5回/日）は
この制約から決まっている。

ここを動かすとユニバースの株価レンジとサイジングが連動して変わる
（`docs/03-universe.md` §1.2・§2）。**変更は人の判断が要る**（CLAUDE.md）。

> かつて `target_position_yen` の上限が15万円（= 30%）になっており、
> #7 の25%と矛盾していた。2026-08-23 に12.5万円へ修正。

### #9 発注冪等性

ネットワーク断は必ず起きる。リトライ時の二重発注を**構造的に**防ぐ：

1. クライアント側で注文IDを採番し、**発注前に永続化**
2. リトライ時はその注文IDで `GET /orders` を照会し、既に通っていないか確認
3. 確認できるまで再発注しない

### #11 キルスイッチ

```bash
# 即時停止（次のループで検知して全手仕舞い）
touch KILL

# API・プロセスが死んでいる場合の手動全手仕舞い
python scripts/close_all_positions.py
```

**ファイルベースにする理由**: プロセスが応答不能でも、
ファイルシステムなら確実に操作できる。ネットワークもAPIも介さない。

`KILL` は `.gitignore` に登録済み。

## 検証（Phase 3 の完了条件）

安全装置は**壊れていることを確認できないと意味がない**。
以下をすべてテストで担保する：

- [ ] レバレッジ超過の発注が**拒否される**ことをテストで確認
- [ ] ショート建玉がストップ注文なしで作れないことをテストで確認
- [ ] 大引けクローズに**障害を注入**（API障害・タイムアウト・部分約定・PC再起動）しても
      最終的に建玉が残らないことを確認
- [ ] 各損失ブレーカーが閾値で**確実に発動**することをテストで確認
- [ ] リトライで**二重発注が起きない**ことをテストで確認
- [ ] reconcile 不一致で**発注が停止する**ことをテストで確認
- [ ] `KILL` ファイルで即時停止することを確認
- [ ] 監査ログから発注を**完全再現できる**ことを確認

> **強制決済ペナルティを1回も発生させないことが、Phase 5 の合格基準に入っている**
> （07-go-live-criteria.md）。

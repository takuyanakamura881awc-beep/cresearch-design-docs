# 09. データ源と2段階構成

**Stage A（口座なし）と Stage B（口座あり）で、使えるデータが変わる。**
本ドキュメントは何が取れて何が取れないかを整理し、
取れないものへの対処を定義する。

---

## 1. 2段階構成

| | Stage A | Stage B |
|---|---|---|
| **口座** | **不要** | 必要（ただし**運用資金は入れない**） |
| **API** | **不要** | kabuステーションAPI |
| データ源 | J-Quants（無料）+ yfinance | 上記 + kabuステーションAPI |
| 内容 | データ基盤・ユニバース・バックテスト・竹の実装・ヒストリカル検証 | ペーパートレード・システム信頼性の検証 |
| 判定 | **戦略に見込みがあるか** | **システムが信頼できるか** |

**Stage A で見込みがなければ、口座を開く必要すらない。**
口座開設・API申込・Windows常設のコストを、戦略の有望性が確認できるまで払わずに済む。

> **口座開設と入金は別。** 口座開設自体は無料・入金不要で、
> kabuステーションAPI も無料。Stage B は「口座は開くが運用資金50万円は入れない」状態。
> ただし Professional プランの条件に信用口座開設と取引実績があるため、
> 最低1回の実取引（数万円程度）が必要な可能性がある（要確認）。

## 2. 口座不要で使えるデータ源

### 2.1 J-Quants API（日本取引所グループ公式）

| 項目 | 内容 |
|---|---|
| 必要なもの | **メールアドレスでのアカウント登録のみ。証券口座は不要** |
| 提供元 | JPX（証券会社ではないため口座の概念がない） |
| 無料プラン | 過去2年分。**ただし12週間遅延** |
| 有料 | Light 1,650円/月〜（直近データ・長い履歴） |
| 認証 | V2 は API キー方式（V1 のリフレッシュトークン方式は廃止済み） |

**取れるもの**: 日足、**日付指定の上場銘柄一覧**、財務、投資部門別売買状況など。

### V2 の仕様（V1 は 2026年6月1日に終了）

**V1 の旧仕様で実装して疎通しなかった実績がある。** パスも項目名も変わっている。

| 項目 | V1（廃止） | V2（現行） |
|---|---|---|
| ベースURL | `https://api.jquants.com/v2` | 同じ |
| 認証 | `x-api-key` ヘッダ | 同じ |
| 銘柄一覧 | `/listed/info` | **`/equities/master`** |
| 日足 | `/prices/daily_quotes` | **`/equities/bars/daily`** |
| レスポンス包み | `{"daily_quotes": [...]}` | **`{"data": [...]}`** |
| 項目名 | `Open` `AdjustmentClose` | **短縮形**（`O` `C` `AdjC` `AdjVo` など） |

### 実測で確認した項目（2026-08-21）

```
日足     AdjC AdjFactor AdjH AdjL AdjO AdjVo C Code Date
         ExRT H L LL MktCap O UL Va Vo
銘柄一覧 CoName CoNameEn Code Date Mkt MktNm Mrgn MrgnNm
         ProdCat S17 S17Nm S33 S33Nm ScaleCat
```

**想定外の収穫があった。** ユニバース構築で代理指標に頼る予定だった項目が直接取れる：

| 項目 | 中身 | 効くフィルタ |
|---|---|---|
| `MktNm` | `"プライム"` | **A（市場）** |
| `Va` | 売買代金 | **B（流動性）** — `終値 × 出来高` の近似が不要に |
| `MrgnNm` | `"貸借"` | **D（売建可否）** — 流動性による代理より正確 |
| `UL` / `LL` | ストップ高/安フラグ | **H（特殊状態）** |
| `S33Nm` | 33業種 | 将来のセクター分散 |

特に `MrgnNm="貸借"` が大きい。**貸借銘柄なら制度信用で売建できる**ので、
「Stage A では売建可否が取れないから流動性で代理する」という妥協が要らなくなった。

> `UL` / `LL` は文字列の `"0"` / `"1"` で返る。`bool("0")` は `True` になるので、
> **文字列をそのまま真偽値にしない**（`data/jquants.py` の `_as_flag`）。

> **日付指定の上場銘柄一覧が取れることが決定的に重要。**
> サバイバーシップバイアスの回避に必須（docs/03-universe.md §4.2）。
> yfinance では代替できない。

**取れないもの**: 分足、板情報、リアルタイム価格。

### 2.2 yfinance（Yahoo Finance）

| 項目 | 内容 |
|---|---|
| 必要なもの | **なし**（ライブラリを入れるだけ） |
| 銘柄指定 | 日本株は `7203.T` のようにサフィックス `.T` |
| 遅延 | 15〜20分（リアルタイムではない） |
| 位置づけ | **非公式API。** 規約・可用性・品質の保証がない |

**取得可能な期間（Yahoo Finance API の制限）**:

| 足 | 公称 | **実測（2026-08-21）** |
|---|---|---|
| 1分足 | 直近7日 | **7日成功 / 9日失敗** |
| 5分足 | 直近60日 | **58日成功 / 60日失敗** |
| 60分足 | 直近730日 | **728日成功 / 730日失敗** |
| 日足 | 制限なし | 402日以上を確認 |

> **公称値ちょうどでは弾かれる。** 「直近60日以内」の判定は境界を含まない。
> `MAX_LOOKBACK_DAYS` は実測値（5m=58、60m=728）を採用している。
> 公称値のままだと、上限ぎりぎりの取得が**エラーなく空になる**。

### 2.3 これが計画に与えた改善

**現行計画の最大のボトルネックが消える。**

当初は「分足はどこからも取れないので、kabuステーションAPI で3ヶ月かけて
自前蓄積してからでないと竹を検証できない」という制約があった。

**yfinance は5分足を過去60日分まとめて取得できるため、待たずに検証を始められる。**
オープニングレンジ・ブレイクアウト（30分レンジ）の検証には5分足で十分。

1分足は7日窓しかないが、**日次でローリング回収すれば蓄積できる**
（週1回でも足りるが、取りこぼしを考えて日次で回す）。

## 2.4 期間ズレ — J-Quants Free と yfinance 5分足は重ならない

**これが Stage A のデータ設計で最も注意すべき点。**

今日を 2026-08-21 とすると：

```
        2024-05        2026-05-29              2026-06-22    2026-08-21
           |                |                       |            |
J-Quants   |================================|       :            :
Free 日足  |     過去2年（12週=84日遅延）     |       :            :
           :                :                       :            :
yfinance   :                :                 |==================|
5分足      :                :                 |   直近60日       |
           :                :<--- 24日の穴 --->|            :
```

**竹の検証には5分足と同じ期間の日足が要る**（ATR%・20日平均売買代金・前日出来高比という
ユニバース構築の指標が日足由来のため）。J-Quants Free だけでは、
**5分足がある期間の日足が1日も取れない。**

### 対処 — 日足は J-Quants を正とし、yfinance で直近84日を補完する

| 期間 | 日足の取得元 |
|---|---|
| 2年前 〜 84日前 | **J-Quants**（JPX公式。分割調整が信頼できる） |
| 84日前 〜 今日 | **yfinance**（`auto_adjust=True` 必須） |

実装は `data/base.py` の `FallbackDataSource([JQuants, Yahoo])`。
**どちらのソースから取ったかは `data/store.py` の `fetch_log` に記録される**ので、
後から「この期間は yfinance 由来」と追跡できる。

### 重複期間で品質を実測する

J-Quants Free（2年前〜84日前）と yfinance 日足（期間制限なし）は**重なる**。
この重複期間で両者の終値を突き合わせれば、**yfinance のズレを自分のデータで実測できる**。

`scripts/verify_data_sources.py` がこれを行う。判断の目安：

- 中央値 0.01% 未満・1%超がゼロ → yfinance の日足は信用できる。**Free のままでよい**
- 1%超が散発する → 分割調整のズレの可能性。**Light（1,650円/月）を検討**

**推測で課金しない。測ってから決める。**

## 2.45 調整基準を揃える — 配当調整を入れてはならない

**J-Quants と yfinance で価格の調整基準が違う。**

| 源 | 分割調整 | 配当調整 |
|---|---|---|
| J-Quants `AdjC` | あり | **なし** |
| yfinance `auto_adjust=True` | あり | **あり**（トータルリターン基準） |
| yfinance `auto_adjust=False` の `Close` | あり | なし ← **これを使う** |

### 実測での発見

7203 の118日を突き合わせたところ **中央値1.467% / 最大1.467%** の差が出た。
**中央値と最大値が一致するのはランダムなノイズではなく、一定のオフセットの証拠。**
トヨタの半期配当の水準と一致する。

### なぜ揃えないといけないか

1. **継ぎ目に実在しない値動きが生まれる** — 日足は「2年前〜84日前は J-Quants、
   直近84日は yfinance」で繋ぐ。基準が違うと継ぎ目に約1.5%の段差ができ、
   そこを跨ぐ **14日ATR や 20日平均が汚染されて架空のシグナルになる**。

2. **株価レンジフィルタがずれる** — 配当調整済み価格は実際の約定価格ではないため、
   300〜3,000円の判定が実態からずれる。

**私たちに必要なのは「実際に約定する価格」**なので、分割のみ調整が正しい基準。
`data/yahoo.py` の `DEFAULT_ADJUST_DIVIDENDS = False` がこれを担保する。

> 基準の違いによる差を「データ品質の差」と誤認して Light に課金しないこと。
> 課金の判断は基準を揃えた後の乖離で行う。

## 2.5 yfinance 運用上の落とし穴と対策

非公式APIであることに起因する4つの問題。すべて `data/yahoo.py` で対処済み。

### 落とし穴1: レート制限とIPブロック

**最も危険。** 短時間に大量のリクエストを投げると Yahoo 側からブロックされるが、
**ブロックされても例外が飛ばず、空の DataFrame が返る。**

つまり「データがない銘柄なのか、ブロックされたのか」が区別できない。
これを「データなし」として黙って受け入れると：

- ユニバースから銘柄が**静かに脱落**する
- バックテストが「その日は取引機会がなかった」と誤認する
- **エラーが出ないので気づけない**

**対策**：空の応答は `EmptyResponseError` を送出して**安全側（例外）に倒す**。
取得は**20銘柄ずつ・バッチ間1秒**。TTL付きキャッシュ（`store.py`）で重複取得を防ぐ。

### 落とし穴2: データの欠損と不整合

- **`auto_adjust=True` を指定しないと分割前後で価格が不連続になる**
  → ATR%・売買代金の計算が壊れ、**架空の急騰・暴落をシグナルとして誤検出**する
- 欠損は `None` ではなく `NaN` で返る → `if value is None` では検出できない

**対策**：`auto_adjust=True` を**引数で無効化できないよう強制**。欠損判定は `pd.notna()`。

### 落とし穴3: 並行処理との相性

yfinance は内部で `~/.cache/py-yfinance/` の SQLite をタイムゾーンキャッシュに使う。
**複数プロセスが同時に読み書きすると `OperationalError` で落ちる。**

本プロジェクトでは日次の分足回収・日足取得・手動のバックテスト実行が並走しうる。
**ローカルで1プロセスしか動かさない開発中は踏まないので、本番で初めて落ちる**類の問題。

**対策**：`yf.set_tz_cache_location()` でプロセス固有の一時ディレクトリに隔離し、
`atexit` で削除する。

### 落とし穴4: 仕様変更・廃止リスク

Yahoo 側のエンドポイント変更で、**ある日突然データが取れなくなる**。
「昨日まで動いていたのに今日から全銘柄 empty DataFrame」という報告が定期的に上がり、
ライブラリが対応するまで**数日間データが取れない**こともある。

**対策**：`data/base.py` の `FallbackDataSource` で**単一データソースに依存しない構成**にする。
日足は J-Quants にフォールバックできる。TTL付きキャッシュも緩衝材として働く
（「昨日のデータで走らせるか、何も走らせないか」なら前者のほうが実用的）。

**ただし5分足にはフォールバック先が存在しない**（J-Quants に分足がない）。
これは設計上の既知の単一障害点で、蓄積データをローカルに確実に残すことで緩和する。

## 3. 口座なしでは取れないもの

| # | 取れないもの | 影響 | 対処 |
|---|---|---|---|
| 1 | **板情報**（bid/ask/厚み） | 約定モデルが粗くなる | スリッページを**保守的に厚く**見積もる（§4） |
| 2 | **寄り前気配** | Layer 2 スコア3指標のうち2つが使えない | 前日引け時点の情報だけで選定する（§5） |
| 3 | **一般信用デイトレの売建可能銘柄リスト** | 売建可否フィルタが使えない | Stage A は流動性上位で代理。Stage B で実データに差し替え |
| 4 | **発注系の動作** | 大引けクローズ・reconcile・冪等性・レバレッジ強制・レート制限が**未検証** | **Stage B が必要**（§6） |

## 4. 約定モデル — 板がない場合の対処

**原則: 検証できないものは、必ず保守的な側（成績が悪くなる側）に倒す。**

| 項目 | Stage A（板なし） | Stage B（板あり） |
|---|---|---|
| 成行の約定価格 | そのバーの**不利な側**（買いは高値寄り、売りは安値寄り）を仮定 | 次ティックの反対サイド気配 |
| 指値の約定判定 | バーのレンジが価格を通過 **かつ** 出来高が十分な場合のみ | 板の通過 + 出来高按分 |
| スリッページ | **厚めに見積もる**（片道 15〜20bps） | 実測値に置換（片道 10bps 前提） |

> **楽観的な約定モデルを使わない。**
> バックテストで勝つ戦略を作るのは簡単だが、それは目的ではない。
> Stage B で実測スリッページに置き換えたときに成績が崩れるなら、
> それは Stage A のモデルが甘かったということ。

## 5. Layer 2 銘柄選定 — 寄り前気配がない場合

当初の Layer 2 スコアは3指標のうち2つが寄り前気配に依存していた。

| 指標 | Stage A | 理由 |
|---|---|---|
| ATR%（14日ATR ÷ 株価） | **使える** | 前日までの日足から計算できる |
| 寄り前ギャップ率 | **使えない** | 寄り前気配が必要 |
| 寄り前出来高比 | **使えない** | 寄り前の板の厚みが必要 |

### Stage A の代替スコア（前日引け時点の情報のみ）

| 指標 | 内容 | 狙い |
|---|---|---|
| **ATR%** | 14日ATR ÷ 株価 | 日中値幅の期待値。**ATR% ≥ 2% は変更なし** |
| **前日出来高比** | 前日出来高 ÷ 20日平均出来高 | 前日に注目が集まったか |
| **前日レンジ%** | (前日高値 − 前日安値) ÷ 前日終値 | ボラティリティの持続性 |
| **前日終値位置** | (終値 − 安値) ÷ (高値 − 安値) | 前日の需給の決着。翌日の初動の方向のヒント |

**この設計は妥協ではない。**
「前日引け時点の情報だけで翌日の監視銘柄を決める」のは実運用でも一般的な方式で、
寄り前気配は流動性が薄くノイズが多いという批判もある。

### Stage B での検証構造

Stage B で寄り前気配が使えるようになったら、**追加して予測力を比較検証する**：

- Stage A スコア単体
- Stage A スコア + 寄り前気配

**寄り前気配が実際に予測力を持つかを実データで判定できる。**
プレミアム枠の寄与検証（docs/03-universe.md §2）と同じ構造。
持たないなら追加しない。

## 6. Stage B を省いた場合に何が起きるか

Stage A の後に Stage B を飛ばして実弾に入ることは技術的には可能。
**ただし以下が未検証のまま本番になる。**

| 未検証項目 | 想定される事故 | 金銭的影響 |
|---|---|---|
| 大引けクローズの信頼性 | 建玉を閉じ損ねる | **1回2,200円**（月利目標の約2日分） |
| 発注の冪等性 | ネットワーク断のリトライで**二重発注** | 意図の2倍の建玉。レバレッジ超過 |
| レバレッジ1倍の強制 | 上限を超えた発注が通る | 最大損失が想定を超える |
| reconcile | 状態のズレを抱えて自動発注を継続 | 把握していない建玉が残る |
| レート制限 | API に弾かれて発注が通らない | 手仕舞いできない |

**合格基準（docs/07-go-live-criteria.md）の「システム障害ゼロ」は、
Stage B なしには判定できない。**

> Stage B を省くかどうかは**人の判断**。
> ただし省く場合は、実弾の初期投入額をさらに小さくする（10万円→3万円など）ことで
> 未検証リスクを金額で抑えることを推奨する。

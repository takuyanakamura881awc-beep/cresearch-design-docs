# 08. 開発ハーネス設計

このプロジェクトを Claude Code で開発するときのロール分担とモデル選択。

`.claude/agents/` にサブエージェントとして定義してあり、
`Agent` ツールで `subagent_type` を指定して呼び出す。

---

## 1. 設計の考え方

### なぜロールを分けるのか

**このプロジェクトは誤りが金銭損失に直結する。** 一般的なソフトウェアなら
バグは「動かない」で済むが、ここでは「意図しない発注」「建玉の閉じ忘れ」が
そのまま現金の損失になる。

そこで、**書く人と検証する人を構造的に分離する**：

| 分離 | 理由 |
|---|---|
| 実装者 ≠ レビュー者 | 自分のコードは自分では見えない |
| 実装者 ≠ テスト作成者 | 実装を見てテストを書くと、実装の追認になる |
| レビュー者 ≠ リスク監査者 | 安全装置は専門の目で見る必要がある |
| 戦略の検証を独立させる | バックテストのバイアスは、コードのバグとは別種の問題 |

**検証系のロールは read-only** にしてある（`tools` に `Write` / `Edit` を持たせていない）。
自分で修正できると、指摘の独立性が失われるため。指摘を返し、修正は実装者が行う。

### モデル選択の基準

| モデル | 使う場面 | 根拠 |
|---|---|---|
| **Opus 5** | 設計判断・レビュー・リスク監査・統計的妥当性の検証 | **誤りが金銭損失に直結する領域。**ここでモデルをケチる意味がない |
| **Sonnet 5** | 仕様が確定した実装・テスト作成・データ処理 | 判断ではなく作業。仕様が明確なら十分な品質が出る |

**判断が要る仕事に Opus、手が要る仕事に Sonnet** という切り分け。

---

## 2. ロール一覧

| ロール | モデル | 権限 | 責務 |
|---|---|---|---|
| **architect**（設計者） | Opus 5 | 読み書き | 設計判断・インターフェース定義・仕様確定 |
| **implementer**（作業者） | Sonnet 5 | 読み書き | 確定した仕様の実装 |
| **data-engineer** | Sonnet 5 | 読み書き | データ取得・整形・永続化（Phase 1 の主担当） |
| **test-writer** | Sonnet 5 | 読み書き | テスト作成（仕様から書く。実装から書かない） |
| **reviewer**（レビュー者） | Opus 5 | **読み取りのみ** | コードの正しさ検証・問題指摘 |
| **risk-auditor**（リスク監査） | Opus 5 | **読み取りのみ** | 安全装置16項目とレバレッジ不変条件の監査 |
| **backtest-validator** | Opus 5 | **読み取りのみ** | バイアス検出・過学習検証・統計的妥当性 |

---

## 3. 各ロールの要点

### architect（設計者）— Opus 5

モジュール間の**境界と契約**を決める。実装の詳細は書かない。

**勝手に決めず人に確認すること**：安全装置の閾値変更、レバレッジ1倍への例外、
合格基準の変更、対象市場・証券会社の変更。

設計判断は根拠つきで `docs/00-overview.md` の意思決定ログに追記する。

### implementer（作業者）— Sonnet 5

**確定した仕様をコードにする。設計判断はしない。**

仕様が曖昧で解釈によって挙動が変わる場面、安全装置を迂回しないと実現できない要求に
出くわしたら、**実装を止めて architect に差し戻す**。
「たぶんこうだろう」で金融ロジックを書かない。

### data-engineer — Sonnet 5

**最優先は `data/recorder.py`（分足蓄積）。**
分足はどこからも取得できず自前蓄積しかないため、
**蓄積開始の遅れがそのまま竹の検証開始の遅れになる**。

データの異常を見つけたら黙って修正せず報告する。
データ異常は戦略の前提を壊すため、人が把握している必要がある。

### test-writer — Sonnet 5

**仕様（`docs/`）を読んでテストを書く。実装を読んで書かない。**

優先度は「正常に動く」より**「危険な操作が拒否される」**が先。
大引けクローズには**障害注入テスト**（API障害・タイムアウト・部分約定・再起動）を必ず書く。

### reviewer（レビュー者）— Opus 5・read-only

お金が消える経路を最優先で見る：発注パラメータの取り違え、
レバレッジチェックの迂回、クローズ処理の漏れ、ショートのストップ欠落、リトライの二重発注。

**推測で指摘しない。** スタイルの好みは `ruff` に任せる。

### risk-auditor（リスク監査）— Opus 5・read-only

**「テストがある」ことを合格としない。テストが正しいことまで確認する。**

`grep` で発注系の呼び出しを列挙し、すべてが `risk/leverage.py` を通っているかを実際に辿る。
能動的に抜け道を探す。

**判断に迷ったら不合格にする。** 「たぶん大丈夫」で実弾に進む方がコストが高い。

### backtest-validator — Opus 5・read-only

3つのバイアス（ルックアヘッド・サバイバーシップ・過学習）を検出する。

ルックアヘッドは「注意して書いている」だけなら**不合格**。
**構造で防いでいること**を要求する。

**成績が良いときほど厳しく見る。** 良すぎる結果は、多くの場合バグかバイアス。

## 4. フェーズ別のロール割り当て

| Phase | 主担当 | 検証 |
|---|---|---|
| 1 データ基盤 | **data-engineer** | reviewer |
| 2 ユニバース + バックテストエンジン | architect → implementer | **backtest-validator** + reviewer |
| 3 API + ペーパー基盤 + 安全装置 | architect → implementer + test-writer | **risk-auditor**（必須） + reviewer |
| 4 竹の実装 + 検証 | implementer + test-writer | **backtest-validator** + reviewer |
| 5 ペーパートレード運用 | data-engineer（監視） | — |
| 6 評価 → 実弾移行判定 | — | **risk-auditor + backtest-validator**（両方必須） |

### 必ずゲートを通すタイミング

以下は**該当ロールの合格なしに次へ進まない**：

| ゲート | 担当 |
|---|---|
| Phase 3 完了判定 | **risk-auditor** |
| ペーパートレード開始前 | **risk-auditor** |
| バックテスト結果の採用判断 | **backtest-validator** |
| **実弾移行前** | **risk-auditor + backtest-validator の両方** |

---

## 5. 使い方

```
# 設計判断が必要なとき
Agent(subagent_type="architect", prompt="...")

# 実装
Agent(subagent_type="implementer", prompt="...")

# 安全装置の監査（Phase 3 完了時・実弾移行前は必須）
Agent(subagent_type="risk-auditor", prompt="docs/05-risk-management.md の16項目を監査して")

# バックテスト結果の検証
Agent(subagent_type="backtest-validator", prompt="...")
```

検証系ロール（reviewer / risk-auditor / backtest-validator）は
**指摘を返すだけで修正しない**。修正は implementer に渡す。

---

## 6. 人間が判断すべきこと

ハーネスに任せてはいけない判断：

- **安全装置の閾値を緩める**（日次-2%、DD-15%、同時5銘柄など）
- **合格基準を変える**（`docs/07-go-live-criteria.md`）
- **実弾に移行する / 投入額を増やす**
- **ブレーカー発動後の再開承認**（連続損失・ドローダウン上限）
- **対象市場・証券会社を変える**

**基準を緩める判断は、必ず人が明示的に行う。**
成績が出ないときに基準を下げたくなるのが人間の常であり、
それをエージェントに追認させると歯止めがなくなる。

## 竹 — デイトレード ロング/ショート（当日決済）★メイン手法

### 概要

| | |
|---|---|
| **銘柄選定** | 03-universe.md のスコアリングで日次50銘柄 → シグナル発生3〜5銘柄にエントリー |
| **保有期間** | 数十分〜大引け前（**当日決済必須**） |
| **信用区分** | **デイトレ信用（手数料0・金利0・貸株料0）** |
| **ポジション** | 同時3〜5銘柄、各10〜15万円。**1日5〜15トレード**（同一銘柄の再回転も可） |
| **期待成績** | 年利 20〜50% / 最大DD 15〜30% |
| **必要データ** | 分足。**Stage A は yfinance の5分足（過去60日分が即座に取れる）**、Stage B は kabuステーションAPI |
| **板情報** | **シグナルには使わない**（下記「板情報の扱い」）。執行と Stage B の品質フィルタでのみ使う |

### なぜメインなのか

- **コスト0** — デイトレ信用は手数料・金利・貸株料すべて0
- **資金効率が最大** — 同一銘柄を1日に何度でも回転できる
- **オーバーナイトリスクなし** — 当日決済。1トレードのテールリスクがスイングより小さい
- **相場環境への依存が小さい** — ロング/ショート両建て

「資金効率が良い方法を選びたい」という要求に最も直接的に応える。

### シグナルA — オープニングレンジ・ブレイクアウト（順張り）

```
9:00-9:30 の高値/安値でレンジを定義
  ↓
レンジ上抜け → ロングエントリー
レンジ下抜け → ショートエントリー
  ↓
ストップ: レンジ反対側 または エントリー価格 - N×ATR
利確:     エントリー価格 + M×ATR
時間切れ: 14:50 に無条件クローズ
```

寄り付き後30分のレンジは、その日の需給の綱引きの結果。
それを抜けることは新しい方向へのエネルギーを示す、という仮説に立つ。

### シグナルB — VWAP乖離の平均回帰（逆張り）

```
価格が VWAP から一定以上乖離
  かつ 乖離が拡大から縮小に転じた
  ↓
VWAP 方向へエントリー（上方乖離ならショート、下方乖離ならロング）
  ↓
利確: VWAP タッチ
ストップ: 乖離がさらに拡大した水準
時間切れ: 14:50 に無条件クローズ
```

VWAP は機関投資家の執行基準になりやすく、そこへの回帰力が働く、という仮説。

> **シグナルAとBは方向が逆になる場面がある。** 同一銘柄で両方が
> 同時発火した場合はエントリーを見送る（矛盾するシグナルは情報がない状態と扱う）。

### 手仕舞い規律

| 条件 | 動作 |
|---|---|
| ATRベースの逆指値ストップ | 建玉ごとに必ず設定。**ショートは特に必須** |
| 利確目標到達 | クローズ |
| **14:50** | **無条件で全建玉を成行クローズ**（02-margin-rules.md §3） |
| 日次損失上限 -2% | 当日全停止 + 全建玉クローズ |

### パラメータ（Phase 4 で確定）

`config/strategies.yaml` に置く。初期値は暫定で、
ウォークフォワード検証で決める（in-sample の成績は成績として数えない）。

- オープニングレンジの時間幅（暫定30分）
- ストップの ATR 倍率
- 利確の ATR 倍率
- VWAP 乖離の閾値
- 同時保有銘柄数（暫定3〜5）

## 松 — スキャルピング（当日決済）／将来的に検討

| | |
|---|---|
| **銘柄選定** | 板が厚く出来高の大きい5〜10銘柄に集中 |
| **シグナル** | 板の厚み・歩み値の偏り・ティック単位のモメンタム |
| **保有期間** | 数秒〜数分 |
| **ポジション** | **1日数十〜百回転**。ただし**発注5req/秒の制限が回転数の上限を決める** |
| **期待成績** | 分散が極めて大きい。年利 -30%〜+80% / 最大DD 30%超 |
| **必要データ** | 板・歩み値のティックデータ（自前蓄積、データ量大） |
| **着手条件** | **竹が実弾で安定稼働した後** |

### 正直な評価

自宅回線 → localhost API → 証券会社という経路のレイテンシでは、
専用線とコロケーションを持つ機関投資家との板の取り合いに勝つのは難しい。
**薄い利幅を狙う手法ほどレイテンシ劣位が効く。**

**竹の実績とレイテンシ実測を見てから着手を判断する。**
優先度は最も低く置く。

## 梅 — 日足スイング ロング/ショート／資金300万円以上で追加

| | |
|---|---|
| **銘柄選定** | クロスセクショナル・モメンタム（過去60〜120日リターンのランキング） |
| **保有期間** | 5〜20営業日（オーバーナイト保有）、週次リバランス |
| **信用区分** | 一般信用（長期）※デイトレ信用は当日決済必須のため使えない |
| **コスト** | **金利・貸株料が発生**（デイトレ信用と違い無料ではない） |
| **期待成績** | 年利 5〜15% / 最大DD 10〜20% |
| **必要データ** | 日足のみ → J-Quants 無料プランで検証可能 |
| **追加条件** | **資金300万円以上**（目安） |

### なぜ資金300万円を条件にするのか

梅は**分散が効いてこそ機能する**手法。

50万円では上位3ロング + 下位2ショートが限界（1銘柄10万円）。
株価レンジの制約（03-universe.md §2）も重なり、
**モメンタム上位から選べる銘柄が大幅に減って戦略の前提が崩れる**。

資金が増えれば**分散数と株価レンジ上限の両方が緩み**、梅が本来の性能を発揮できる。

### 竹との併用

竹（日中・当日決済）と梅（スイング・オーバーナイト）は**時間軸が異なるため併用可能**。
資金配分を分ければ互いのポジションが干渉しない。

ただし**レバレッジ1倍の不変条件は両手法の合計に対して適用する**。
竹の建玉 + 梅の建玉 ≤ 現金残高。

## 板情報の扱い

**「デイトレードなのになぜ板を見ないのか」への回答。** シグナルと執行を分けて整理する。

### 竹は板を「シグナル」に使わない

竹のシグナル（オープニングレンジ・ブレイクアウト、VWAP乖離）は
**5分足の OHLCV だけで計算でき、板情報を必要としない**。これは意図的な設計判断。

**理由1: 時間軸が合わない（本質）**

板の厚みや指値の偏りが価格を予測するのは**数秒〜数分**のスケール。
竹の保有期間は数十分〜大引けなので、**エントリー時点の板の状態は数十分後にはほぼ無関係**になる。

逆に言えば、板を主シグナルにするなら保有期間も数分にすべきで、それはもう松（スキャルピング）。
**板を使う手法と、板を使わず数十分持つ手法は別物**で、混ぜると中途半端になる。

**理由2: 板を見る手法ほどレイテンシ勝負になり、個人が構造的に不利**

自宅回線 → localhost API → 証券会社という経路では、専用線とコロケーションを持つ
機関投資家に勝てない。**板を読んでから発注するまでの間に、相手はもう動いている。**
薄い利幅を狙う手法ほどこの劣位が効く。松を後回しにする判断の根拠でもある。

**理由3: Stage A では板が取れない**

口座なしでは検証できない。ただしこれは3番目の理由で、1と2が本質。
**板が取れる環境でも竹には使わない。**

### 板は「執行」には効いており、既に設計に入っている

シグナル判断に使わなくても、発注時には板が効く。対応関係は以下の通り。

| 板への配慮 | 実装箇所 |
|---|---|
| 10〜15万円の注文が板を動かさない水準の確保 | `universe/filters.py` フィルタB（20日平均売買代金10億円以上） |
| 板がない前提の保守的な約定モデル（片道20bps） | `broker/replay.py`、`config/strategies.yaml` の `execution_cost.stage_a` |
| 実測の板を使う約定モデル（片道10bps） | `broker/paper.py`、`config/strategies.yaml` の `execution_cost.stage_b` |

### Stage B で板を「エントリー品質フィルタ」として足し、比較検証する

板をシグナルの主役にはしないが、**エントリーの品質フィルタ**としてなら竹の時間軸でも効きうる：

- ブレイクアウト時に板が薄い → 見せ板・流動性不足の可能性 → **見送る**
- 反対側の板が厚い → ブレイクが失敗しやすい → **見送る**
- 成行のインパクト推定 → **発注サイズを調整する**

**足して成績が上がるかを実データで判定する。**
寄り前気配（`docs/09-data-sources.md` §5）・プレミアム枠（`docs/03-universe.md` §2）と
同じ検証構造。**上がらなければ足さない。**

設定は `config/strategies.yaml` の `take_intraday.orderbook_filter`（既定 `enabled: false`）。
実装は Stage B（Phase 4）。

## 実装方針

`strategy/base.py` に抽象インターフェースを置く。
**3手法すべてを想定して設計する**：

- long / short 両対応
- 保有期間の違いを吸収できる形（数秒〜数週間）
- シグナル生成（`bars → signals`）と執行を分離する

Phase 4 時点では `strategy/take_intraday.py`（竹）のみを実装する。
`matsu_scalp.py` と `ume_swing.py` は同じ抽象に従って後から追加する。

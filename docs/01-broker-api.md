# 01. kabuステーションAPI の仕様と制約

三菱UFJ eスマート証券（旧 auカブコム証券）が提供する個人向け発注API。
本プロジェクトの発注経路。

> **本ドキュメントの内容はすべて Stage B（口座あり）の話。**
> Stage A（Phase 1〜3）は口座もAPIも不要で進む（docs/09-data-sources.md）。

> 本ドキュメントは調査時点の情報。実装前に公式ポータル
> （https://kabucom.github.io/kabusapi/ptal/）で最新仕様を確認すること。

---

## 1. 基本構成

| 項目 | 内容 |
|---|---|
| 形式 | REST API + WebSocket |
| エンドポイント | `http://localhost:18080/kabusapi`（本番） / `18081`（検証） |
| 対応OS | **Windows 専用** |
| 前提 | kabuステーションアプリが**同一PCで常駐**していること |
| 利用条件 | kabuステーション **Professionalプラン以上**（利用料は無料） |
| 申込 | ログイン後画面 →「ピックアップサービス」→「kabuステーション®」→「kabuステーション®API」 |

**アーキテクチャ上の含意**: API はクラウドではなくローカルの常駐アプリが提供する。
つまり **PC が落ちればシステムも落ちる**。ハートビート監視（05-risk-management.md #16）と
PC 再起動からの自動復帰が運用設計の必須要件になる。

### Professionalプランの条件

信用取引口座の開設と取引実績が必要とされる。
**本プロジェクトは信用取引を前提とするため、この条件は自然に満たされる。**

> 正確な条件は口座開設時に要確認（09 未決事項）。

## 2. 認証

1. `.env` の `KABUS_API_PASSWORD` を使って `POST /token` を呼ぶ
2. 返却された `X-API-KEY` を以降の全リクエストのヘッダに載せる
3. トークンには有効期限があるため、**失効時の自動再取得**を実装する

パスワードは kabuステーションアプリの [システム設定] → [API] タブで設定する。
本番用と検証用で別々に設定できる。

---

## 3. 主要エンドポイント

| 用途 | エンドポイント | 備考 |
|---|---|---|
| 認証 | `POST /token` | `X-API-KEY` を取得 |
| 発注 | `POST /sendorder` | 現物・信用の新規/返済すべてここ |
| 注文取消 | `PUT /cancelorder` | |
| 注文一覧 | `GET /orders` | 注文状態の確認 |
| **建玉一覧** | `GET /positions` | **reconcile と大引け残存確認の要** |
| 余力 | `GET /wallet/margin` | 信用余力。レバレッジ判定に使う |
| 時価・板 | `GET /board/{symbol}` | |
| 銘柄情報 | `GET /symbol/{symbol}` | 単元株数・値幅制限など |
| 銘柄登録 | `PUT /register` | WebSocket 配信対象の登録 |
| 銘柄登録解除 | `PUT /unregister` / `PUT /unregister/all` | |

### 発注パラメータ（信用取引）

| パラメータ | 値 | 意味 |
|---|---|---|
| `CashMargin` | `1` | 現物 |
| | `2` | **信用新規** |
| | `3` | **信用返済** |
| `MarginTradeType` | — | 信用区分（制度 / 一般長期 / **デイトレ**） |
| `ClosePositionOrder` | — | 返済順序の指定 |
| `ClosePositions` | — | 返済する建玉の個別指定 |

> **`ClosePositionOrder` と `ClosePositions` は同時指定できない。** どちらか一方のみ。
> 本プロジェクトは建玉を個別に管理するため、原則 `ClosePositions` を使う。

## 4. 制約 — 設計を規定する要素

### 4.1 レート制限

| 系統 | 上限 |
|---|---|
| **発注系** | **5 req/秒** |
| 情報系・残高系 | 10 req/秒 |

**自前のスロットラーを必ず実装する**（05-risk-management.md #8）。
API 側の制限に当てて弾かれるのではなく、こちらで待つ。

> この 5 req/秒 が、将来の松（スキャルピング）の回転数の**物理的な上限**を決める。
> 同時に、証券会社側が別途「一定時間内の発注件数」のフロー制限を課している。

### 4.2 WebSocket のリアルタイム配信は同時50銘柄まで

**これが日次銘柄選定の枠を直接規定する**（03-universe.md）。
Layer 1 で絞った100〜200銘柄から、Layer 2 のスコアリングで**上位50銘柄**を選んで登録する。

登録銘柄の入れ替えは `PUT /register` / `PUT /unregister` で行うが、
場中の頻繁な入れ替えは避け、**寄り前に確定させる**設計にする。

### 4.3 分足データが取得できない

kabuステーションAPI はリアルタイムの板・時価を配信するが、**過去の分足は提供しない**。
J-Quants にも分足はない（日足・財務が中心）。

**ただし Stage A では yfinance で代替できる**（docs/09-data-sources.md §2.2）。
yfinance は5分足を過去60日分まとめて取得できるため、
**kabuステーションAPI での蓄積を待たずに竹の検証を始められる**。

`data/recorder.py`（WebSocket からの自前蓄積）は **Stage B の担当**。
Stage A で貯めた5分足より細かい粒度が必要になった場合、
および実運用でのリアルタイム記録に使う。

## 5. 実装方針

### 5.1 Broker 抽象インターフェース

`broker/base.py` に抽象インターフェースを置き、`kabus.py`（実発注）と
`paper.py`（ペーパートレード）を同一インターフェースで差し替える。

**バックテスト・ペーパー・実弾で同じコードパスを通すことが、
シミュレーションと本番の乖離を防ぐ唯一の確実な方法。**
将来の証券会社・市場の移行の受け口も兼ねる。

### 5.2 発注の冪等性

ネットワーク断は必ず起きる。リトライ時の二重発注を**構造的に**防ぐ：

1. クライアント側で注文IDを採番し、**発注前に永続化**する
2. リトライ時は永続化した注文IDで `GET /orders` を照会し、既に通っていないか確認する
3. 確認できるまで再発注しない

### 5.3 起動時 reconcile

想定建玉と `GET /positions` の実建玉を突合する。
**不一致なら発注を停止して通知**する。
状態のズレを抱えたまま自動発注を続けるのが最も危険。

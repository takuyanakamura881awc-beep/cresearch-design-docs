# 06. 運用手順

完全自動運転が前提だが、**人が確認すべき点と、人しかできない介入**を定義する。

> **本ドキュメントの内容は Stage B（口座あり・ペーパートレード以降）の話。**
> Stage A（ヒストリカル検証）には場中の運用がない（docs/09-data-sources.md）。

---

## 1. 1日のスケジュール

| 時刻 | 処理 | 主体 |
|---|---|---|
| 07:00 | ユニバース構築（Layer 1）— 流動性・株価レンジ・売建可否・除外条件 | 自動 |
| 08:00-08:55 | 日次銘柄選定（Layer 2）— スコアリング → 上位50銘柄を WebSocket 登録 | 自動 |
| 08:55 | **起動時 reconcile** — 想定建玉とAPI実建玉を突合 | 自動 |
| 09:00 | 場開始。分足 Recorder 稼働、シグナル監視開始 | 自動 |
| 09:30 | オープニングレンジ確定 → シグナルA の判定開始 | 自動 |
| 09:00-14:50 | シグナル発生でエントリー / ストップ・利確でクローズ | 自動 |
| **14:50** | **全建玉クローズ → `GET /positions` で残存確認** | 自動 |
| 15:30 | 場終了 | — |
| 16:00 | 日次レポート生成・通知 | 自動 |
| 16:00 | **日次レポートの確認** | **人** |

> `08:55` の reconcile で不一致が出た場合、**その日は発注しない**。
> 状態のズレを抱えて自動売買を始めるより、1日休む方が安い。

---

## 2. 人が毎日やること

**日次レポート（16:00 通知）を確認する。** 所要5分。

| 確認項目 | 異常の兆候 |
|---|---|
| **建玉残存: 0** | **1件でも残っていれば即対応**（翌日2,200円のペナルティ） |
| 損益 | 日次損失上限（-2%）への接近 |
| トレード数 | 想定（3〜5）から大きく外れていないか |
| 発注エラー・リトライ回数 | 増加傾向はAPIかネットワークの問題 |
| reconcile 結果 | 不一致はシステムの状態管理の破綻 |
| スリッページ実測 | 想定を超えていればコストモデルの見直しが必要 |

## 3. 人しかできない介入

### 3.1 緊急停止

```bash
# 即時停止（次のループで検知 → 全手仕舞い）
touch KILL
```

**プロセスやAPIが応答不能な場合の手動全手仕舞い:**

```bash
python scripts/close_all_positions.py
```

このスクリプトは**戦略ロジックを一切通さず、建玉を成行でクローズすることだけ**を行う。
システムの他の部分が壊れていても動くように、依存を最小化して実装する。

### 3.2 ブレーカー発動後の再開承認

| ブレーカー | 復帰 |
|---|---|
| 日次損失上限（-2%） | **翌営業日に自動復帰** |
| 連続損失（3営業日） | **人の明示承認が必要** |
| ドローダウン上限（-15%） | **人の明示承認が必要** |

連続・累積のブレーカーは、戦略が現在の相場に合っていない可能性を示す。
**原因を確認せずに再開しない。**

再開手順:
```bash
python scripts/resume_trading.py --acknowledge "<再開理由>"
```
再開理由は監査ログに残す。「なぜ再開してよいと判断したか」を後から辿れるようにする。

## 4. 障害時の対応

| 障害 | 検知 | 対応 |
|---|---|---|
| **kabuステーション停止** | ハートビート | 建玉があれば手動クローズ。アプリ再起動 |
| **PC 再起動・停電** | ハートビート断 | 復帰後 reconcile → 建玉があれば即クローズ |
| **API トークン失効** | 401 応答 | 自動再取得（実装済み前提）。失敗時は停止 |
| **ネットワーク断** | タイムアウト | リトライ（冪等性で二重発注を防止）。復帰しなければ停止 |
| **reconcile 不一致** | 起動時チェック | **発注停止 + 通知。** 手動で原因を確認するまで再開しない |
| **注文が約定しない** | 注文一覧の監視 | 一定時間で取消 → 成行で再発注 |
| **建玉が大引けに残った** | 15:00 の残存確認 | **即座に手動クローズ。** 翌営業日まで持ち越さない |

### 最悪ケースの想定: 場中にPCが落ち、建玉が残る

1. 別の端末から証券会社の Web/アプリにログインし、**手動で建玉をクローズする**
2. これが**唯一確実な最終手段**。システムに依存しない経路を常に確保しておく
3. スマートフォンに証券会社アプリを入れ、ログインできる状態にしておくこと

> **この手順を実際に一度試しておく。** 緊急時に初めて操作するのでは遅い。

## 5. 定期メンテナンス

| 頻度 | 作業 |
|---|---|
| 週次 | 分足データの欠損チェック（Recorder が取りこぼしていないか） |
| 週次 | スリッページ実測 vs モデルの乖離確認 |
| 月次 | バックテストの再実行（蓄積が増えた分足で） |
| 月次 | ユニバース通過銘柄数の推移確認 |
| 随時 | Windows Update の適用（**場中を避ける**。自動再起動を無効化しておく） |

### Windows PC の設定（Stage B に入る時点で一度だけ）

- **スリープ・休止状態を無効化**
- **Windows Update の自動再起動を無効化**（場中の再起動は致命的）
- kabuステーションの**自動起動・自動ログイン**設定
- 電源断対策（UPS の検討）

## 6. ペーパートレード期間中の運用

**ペーパートレードは本番と同じ運用手順で回す。** 手順そのものを検証するため。

- 日次レポートの確認を毎日行う（実弾でないからと省略しない）
- 大引けクローズも同じロジックを毎日走らせる（約60回の実行実績を作る）
- 障害が起きたら本番と同じ手順で対応し、**手順の不備を洗い出す**

> ペーパー期間は「戦略の検証」であると同時に「**運用手順とシステムの検証**」でもある。
> 07-go-live-criteria.md の合格基準に「システム障害ゼロ」が入っているのはこのため。

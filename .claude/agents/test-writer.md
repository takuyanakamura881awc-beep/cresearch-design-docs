# テスト作成者

## 役割

**実装が仕様どおりに動くこと、そして壊れるべきときに壊れることを検証する。**

`implementer` とロールを分けているのは、**実装者が自分のコードにテストを書くと、
書いたとおりに動くことだけを確認するテストになりやすい**ため。
仕様（`docs/`）を読んでテストを書く。実装を読んでテストを書かない。

## 優先度

### 最優先 — 安全装置（`docs/05-risk-management.md`）

**「正常に動く」より「危険な操作が拒否される」ことを先にテストする。**

- レバレッジ超過の発注が**拒否される**
- ストップなしのショート建玉が**作れない**
- レート制限を超える発注が**待たされる**
- reconcile 不一致で発注が**停止する**
- `KILL` ファイルで**即時停止する**
- 各損失ブレーカーが閾値で**発動する**

### 次点 — 障害注入

大引けクローズ（最重要コードパス）に障害を注入し、
**最終的に建玉が残らない**ことを確認する：

- API がエラーを返す
- API がタイムアウトする
- 部分約定で終わる
- プロセスが途中で落ちて再起動する

### 通常 — 境界値

- 単元株の端数処理（100株未満が発生しないこと）
- 株価レンジの境界（300円、2,000円、3,000円ちょうど）
- プレミアム枠の判定（スコア中央値×1.3ちょうど）
- 営業日・大引け時刻の境界
- 板が空、株価0、ゼロ除算

## 書き方

- `pytest` を使う
- **失敗したときに原因がわかるアサーションを書く。**
  `assert result` ではなく、何がどう違うかがわかる形にする
- 外部API（kabuステーション / J-Quants）はモックする。**実発注のテストを書かない**
- テスト名は日本語コメントで意図を補足してよい

## やらないこと

- 実装を読んで「こう動くはずだから」でテストを書く（仕様から書く）
- カバレッジ稼ぎのための意味のないテスト

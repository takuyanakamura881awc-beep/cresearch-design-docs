# データエンジニア

## 役割

市場データの取得・整形・永続化。**Phase 1 の中心的な担い手。**

## 担当モジュール

| モジュール | 内容 |
|---|---|
| `data/jquants.py` | J-Quants V2 日足取得（APIキー方式） |
| `data/recorder.py` | **分足のリアルタイム蓄積（WebSocket → Parquet）** |
| `data/shortable.py` | 一般信用売建可能銘柄・空売り価格規制の日次取得 |
| `data/calendar.py` | 営業日・決算発表日カレンダー |
| `data/store.py` | ローカルデータストア（Parquet + SQLite） |

## 最優先事項

**`data/recorder.py` を最も早く、最も確実に動かす。**

分足は J-Quants にも kabuステーションAPI の履歴にも存在せず、
**自前で蓄積するしかない**。蓄積開始の遅れがそのまま竹の検証開始の遅れになる
（`docs/00-overview.md` のスケジュール制約）。

Recorder に求められる性質：
- **毎営業日、確実に動く**（起動失敗を検知して通知する）
- **取りこぼしを検出できる**（欠損バーがわかる形で記録する）
- **プロセスが落ちても、それまでのデータが失われない**（逐次書き出し）

## 守ること

1. **認証情報をコードに書かない。** `.env` から環境変数経由でのみ読む
2. **API のレート制限を守る**（J-Quants・kabuステーションAPI ともに）
3. **取得したデータをそのまま信用しない。** 欠損・異常値・重複を検出する
4. **データファイルをコミットしない。** `data/` は `.gitignore` 済み
5. **再取得可能にする。** 同じ日付を再取得しても壊れない冪等な設計にする

## データ品質チェック

取得したデータに対して最低限：
- 営業日なのにデータがない銘柄がないか
- 前日終値から異常に乖離していないか（分割・併合の未調整を検出）
- 出来高0のバーが連続していないか
- 時刻の重複・欠落がないか

**異常を見つけたら黙って修正せず、報告する。**
データの異常は戦略の前提を壊すため、人が把握しておく必要がある。
